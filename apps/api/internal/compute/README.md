# 目录说明：apps/api/internal/compute

## 1. 目录职责

本目录实现 Go Compute API Phase 4A compute lifecycle。

本目录负责：

- Job create/get/list/cancel/result/events。
- Worker register/claim/heartbeat/artifact/succeed/fail。
- Model catalog snapshot registration/read/list endpoints, default parameter set status transitions, read-only default parameter set promotion plans, evidence-backed default parameter set approval promotion, and benchmark case job scheduling。
- Model benchmark case metadata and queueing for governance smoke。
- Benchmark run execution history persistence/list/read endpoints。
- Model run persistence plus read/list lookup。
- Process graph registry and ProcessGraph-to-SimulationInput resolution for simulation checks。
- Simulation input registry used by reference-based simulation checks。
- Evidence package export from completed job metadata。
- Simulation check creation from `simulation_request.v1` into queued `compute_job.v1`。
- Artifact retention metadata recording。
- Risk findings copied into stored result summary for read-only integrations。
- Evidence reference dereference for model run, artifact, job, process graph, and embedded simulation input refs。
- Evidence governance summary generated from model runs and the latest persisted model catalog, with built-in fallback。
- Read-only production readiness report generated from evidence governance and stored risk findings。
- Contract validation for existing Agent / simulation / constraint draft / draft confirmation / result explanation schema files。
- Draft confirmation audit record persistence and readback。
- Read-only advisory constraint application plan generation for approved constraint draft confirmations。
- Result explanation submit/review/publish audit workflow with job-scoped evidence ref checks。
- Explicit approved Agent draft promotion to simulation-check jobs when the embedded proposed request is schema-valid。
- Admin-scoped artifact retention sweep HTTP endpoint with safe dry-run default。
- Disabled-by-default artifact retention scheduler helper。
- Opt-in local filesystem or S3-compatible archive backend metadata and download fallback。
- Prometheus metrics snapshot rendering through a read-only metrics service, including archived artifact metadata count。
- Static bearer token scope auth with config-level revocation。
- Token-scoped tenant/project/site read filtering for job list/get and artifact download。
- Selected mutation audit event envelopes for job create/queue and artifact retention delete/archive events。
- Contract validation、canonical payload hash、idempotency/conflict。
- Metadata store abstraction and PostgreSQL implementation。

本目录不负责：

- Python simulation execution。
- Desktop local runtime。
- Frontend UI。

## 3. 维护约定

1. Create job idempotency and payload conflict behavior must stay deterministic.
2. List APIs use stable cursor pagination.
3. Worker state transitions must be validated server-side.
4. Error responses should map to `contract_error.v1`-style structures where applicable.
5. Local development CORS is intentionally limited to loopback browser origins for Web UI smoke tests; checksum visibility is limited to exposed `X-Artifact-Checksum` / `X-Evidence-Checksum` headers; do not broaden origins or exposed headers without an explicit deployment/auth review.
6. Successful compute results may include `runtime_audit.model_runs`; stable extraction and present `job_id` consistency precheck live in `apps/api/internal/domain/models`, while schema validation, raw JSON persistence adapter, and store writes stay in job lifecycle. Persist schema-valid `model_run.v1` records without storing large artifact contents in metadata tables, and keep list filters limited to indexed governance fields such as `job_id`、`model_key` and `model_version`.
7. Evidence package export must reference artifacts/model runs by id and include a checksum header that browser clients can read through the local CORS expose list; do not inline artifact bytes.
8. Contract validation endpoints use existing `job:create` scope; `/contracts/validate` validates only schema files compiled by `ContractValidator` through the platform contracts document validation helper, while `/contracts/confirm-draft` additionally validates the embedded draft, persists a draft confirmation audit record, and returns a warning that no compute job was created. `/contracts/confirmations/{confirmation_id}/constraint-application-plan` uses `job:read`, requires an approved `constraint_draft.v1` confirmation, and returns advisory metadata only; it must not create compute jobs, mutate the target, or mark production approval complete. Stable advisory plan shape and warnings live in `apps/api/internal/domain/agent`. `/contracts/confirmations/{confirmation_id}/promote-simulation-check` is the only promotion path: it requires an approved `agent_scenario_draft.v1` confirmation and a schema-valid embedded `simulation_request.v1`; stable proposed request extraction lives in `apps/api/internal/domain/agent`, while schema validation and job creation stay here. Unknown future contracts must remain invalid until the schema exists.
9. Static token rotation is represented by overlapping token config and setting old token records to `revoked=true`; revoked tokens must fail authentication even if their scopes match. Token config may include `tenant_id`, `project_id`, and `site_id`; when present, job list/get and artifact download HTTP reads must be constrained to matching job context. Empty tenant/project/site remains global for existing dev/admin tokens. Explanation review/publish mutations require `explanation:write` in addition to the route-level read boundary.
10. Model catalog GET endpoints use `job:read`; `POST /api/v1/model-catalog` uses `model:write` to register schema-valid `model_catalog.v1` snapshots. Reads prefer the latest persisted `default` catalog and fall back to the built-in catalog when no snapshot exists. The built-in catalog includes material_balance with an approved default parameter set plus ASM1Slim/ASM1/ASM3/UDM worker-smoke-backed model versions and benchmark cases without default parameter sets. Its stable document shape lives in `apps/api/internal/domain/models`; material-balance default parameter hash generation, typed DTO conversion, contract schema validation, persisted snapshot preference, store writes, and HTTP response mapping remain here. `GET /api/v1/model-catalog/snapshots` lists persisted snapshots only and does not emit the built-in fallback as history. `GET /api/v1/model-catalog/{model_key}/versions/{model_version}/default-parameter-set/promotion-plan` is advisory-only: it checks latest benchmark_run/model_run evidence for the current default parameter set and reports whether a `validated` set is ready to be manually promoted to `approved`; it must not execute benchmarks, mutate catalog snapshots, or mark production approval complete. `POST /api/v1/model-catalog/{model_key}/versions/{model_version}/default-parameter-set/promote-approved` uses `model:write`, reuses the same promotion plan as a gate, and only then stores a new catalog snapshot that changes the current default parameter set to `approved`; it must not execute benchmarks, record `benchmark_run.v1`, or mark production approval complete. `POST /api/v1/model-catalog/{model_key}/versions/{model_version}/benchmark-cases/{benchmark_case_id}/schedule-run` uses `job:create` and only queues a standard `compute_job.v1` for an active model version's validated benchmark case after resolving the existing simulation input reference and checking the current default parameter set exists and is not retired. Its stable job document shape lives in `apps/api/internal/domain/models`; catalog lookup, gate/error mapping, execution profile lookup, simulation input resolution, JSON marshaling, idempotent createJob, store writes, and HTTP response mapping remain here. It does not execute Python, record `benchmark_run.v1`, mutate catalog snapshots, or mark production approval complete. `POST /api/v1/model-catalog/{model_key}/versions/{model_version}/default-parameter-set/status` updates the existing default parameter set status through allowed forward transitions or retirement and stores a new catalog snapshot. This is still not multi-parameter-set management or an automated approval workflow.
11. Benchmark run history endpoints record schema-valid `benchmark_run.v1` only after checking the target benchmark case is present/validated, the parameter set matches the current default parameter set, the referenced model_run exists with matching model/version/parameter hash, and evidence refs resolve inside the model_run job. They must not create or execute benchmark jobs, mutate parameter set status, or mark production approval complete. List queries may filter by `benchmark_case_id` and `parameter_set_id`; the promotion plan relies on the newest passed run per validated benchmark case for the current default parameter set.
12. Artifact upload defaults `retention_policy` to `retain_forever`; when workers provide `ttl` / `archive_candidate` and optional `retain_until`, the API records those fields. `POST /api/v1/admin/artifacts/retention-sweep` requires `artifact:admin`, defaults to `dry_run=true`, can delete expired unreferenced `ttl` artifacts, and writes an audit event envelope; artifacts referenced by model_run evidence refs are protected. When `archiveArtifacts` is configured, expired unreferenced `archive_candidate` artifacts are copied to the configured archive backend (`local_fs_archive` or path-style `s3_archive`), checksum-verified, recorded in durable archive metadata, logged as `artifact.archived`, and then removed from hot storage while normal artifact download falls back to the archive copy. Without an archive store, `archive_candidate` remains skipped with `archive_executor_not_configured`. Archive handling must follow `.ai/decisions/0010-artifact-archive-backend-boundary.md`. The scheduler helper reuses this service method and is only started by the command entrypoint when explicitly configured.
13. When a valid `compute_result.v1` includes top-level `risk_findings`, copy those findings into the stored summary through `apps/api/internal/domain/evidence.StoredResultSummary` so result read APIs expose them without storing the full result payload in metadata tables. Job lifecycle still owns schema validation, result hashing, persistence, and failed-worker completion parsing after `apps/api/internal/domain/jobs.FailedWorkerComputeResult` constructs the fallback result document. Evidence-read integrations can call `GET /api/v1/compute/jobs/{job_id}/evidence-ref?ref=...` to resolve supported refs only within that job boundary; do not dereference refs across unrelated jobs. Supported refs are `model_run:<id>`、`artifact:<id>`、`job:<id>`、`simulation_input:<id>`、`process_graph:<id>` and generated `evidence_package:<id>`；stable evidence ref parsing lives in `apps/api/internal/domain/evidence`.
14. Evidence governance uses the latest persisted model catalog, with built-in fallback, to mark model version and parameter set status; `production_allowed=true` currently requires an active model version and matching approved default parameter set. That pure model-run production governance gate lives in `apps/api/internal/domain/models`, while store-backed catalog lookup and evidence package assembly remain here. `GET /api/v1/compute/jobs/{job_id}/production-readiness` uses `evidence:read` and returns schema-valid `production_readiness.v1`: job not succeeded, `governance.production_allowed=false`, or high/critical `risk_findings` block readiness; medium findings only warn. The stable `risk_findings` extraction, severity summary, and production-readiness policy evaluation rules live in `apps/api/internal/domain/evidence`. The report is read-only, keeps `external_approval_required=true` and `auto_publish_allowed=false`, and must not mutate jobs/catalogs or mark production approval complete.
15. Process graph registration stores only schema-valid `process_graph.v1` payload metadata and hash in the metadata DB. Stable material-balance process graph structure validation and ProcessGraph-to-SimulationInput projection live in `apps/api/internal/domain/simulation`; this package keeps schema validation, metadata record assembly, idempotency, store access, HTTP mapping, and evidence-ref lookup. The API currently resolves `simulation_request.v1.input_ref.process_graph_id` by loading a registered process graph and generating a `simulation_input.v1` payload for material-balance jobs; it does not execute simulation directly and must not infer ASM/UDM process graph semantics.
16. Simulation check creation is a thin adapter from external `simulation_request.v1` to internal `compute_job.v1`; it validates embedded `input_ref.simulation_input`, resolves a previously registered `input_ref.simulation_input_id`, or replays a persisted `input_ref.model_run_id` by reusing the source job's original `simulation_input.v1` payload before queueing for material_balance/ASM1Slim/ASM1/ASM3/UDM job types. The stable job type to execution profile / worker capability mapping and pure simulation check job document assembly live in `apps/api/internal/domain/simulation`. Registered `input_ref.process_graph_id` resolution remains material-balance-only.
17. Simulation input registration stores only `simulation_input.v1` payload metadata and hash in the metadata DB; it must not store simulation results, time-series artifacts, or approval state.
18. Result explanation workflow stores externally generated `result_explanation.v1` payloads only after schema validation and job-scoped evidence ref resolution. Stable top-level and statement-level result explanation evidence ref extraction lives in `apps/api/internal/domain/evidence`. Review/publish changes audit status only; it must not generate explanation text, execute Agent code, mark production approval complete, or mutate jobs/results.
19. `/metrics` renders a read-only snapshot from the metadata store: API up, jobs by status, registered workers, artifact metadata count, archived artifact metadata count, and retention candidates. Metrics rendering must not trigger retention sweep, timeout sweep, or any lifecycle mutation.
20. `Store` is the aggregate metadata store. Domain metadata interfaces live in `store.go`; artifact metadata uses `ArtifactMetadataStore` because `artifacts.go` already owns the byte/object `ArtifactStore` abstraction.
21. Artifact upload, job artifact listing, artifact metadata lookup, download, retention sweep, and archive copy/checksum/delete logic live in `ArtifactLifecycleService`; its constructor should stay limited to `ArtifactLifecycleStores` (`JobStore`, `ArtifactMetadataStore`, `ArchiveMetadataStore`), `ArtifactObjectStores` (hot and archive object stores), the contract validator, and a clock. Stable artifact retention policy parsing, candidate checks, and retention sweep action planning live in `apps/api/internal/domain/artifacts`.
22. Simulation input registration, process graph registration, `simulation_request.input_ref` resolution, material-balance ProcessGraph-to-SimulationInput schema/store orchestration, and model-run replay input lookup live in `SimulationInputService`; its constructor should stay limited to `SimulationInputStore`, `ProcessGraphStore`, `ModelRunReplayStore` (`ModelRunStore` + `JobStore`), the contract validator, and a clock. Stable process graph validation/projection rules live in `apps/api/internal/domain/simulation`.
23. Draft confirmation persistence, constraint application planning, and explicit Agent draft promotion live in `DraftWorkflowService`; its constructor should stay limited to `DraftConfirmationStore`, the contract validator, a clock, and the existing simulation-check creation callback. Stable constraint application advisory plan assembly and `agent_scenario_draft.v1.proposed_request` extraction live in `apps/api/internal/domain/agent`; confirmation lookup, approval/schema gating, schema validation, JSON marshaling, simulation-check job creation, HTTP mapping, and store writes remain here.
24. Result explanation submit/review/publish lives in `ResultExplanationService`; its constructor should stay limited to `ResultExplanationStore`, `JobStore`, the contract validator, a clock, and the existing job-scoped evidence resolver callback. Stable result explanation evidence ref extraction lives in `apps/api/internal/domain/evidence`.
25. Model catalog reads/writes, default parameter set status/promotion planning, benchmark run history, model run lookup, and benchmark case queueing live in `ModelGovernanceService`; its constructor should stay limited to `ModelGovernanceStores` (`ModelCatalogStore`, `BenchmarkRunStore`, `ModelRunStore`), the contract validator, a clock, `SimulationInputService.ResolveSimulationInput`, the existing compute-job creation callback, and the existing job-scoped evidence resolver callback. Stable built-in model catalog document shape, benchmark case run job document shape, compute result model_run extraction/precheck, `model_run.v1` raw identity/ref/warning/parameter_hash parsing, model-run identity/hash comparison, `benchmark_run.v1` evidence ref parsing, benchmark case scheduling / benchmark run admission gate, single benchmark case promotion readiness, default parameter set status transition invariants, the pure default-parameter-set promotion gate, and the pure model-run production governance gate live in `apps/api/internal/domain/models`; built-in catalog document shape is used by the no-persisted-catalog fallback before compute calculates the material-balance parameter hash and converts to typed DTOs, benchmark case run job document assembly is used after compute has loaded the catalog, checked gates, looked up the execution profile, resolved the simulation input, and checked job_type consistency but before compute marshals and calls createJob, model-run extraction is used by job completion before compute applies schema validation and persistence, model-run parsing is shared by MemoryStore/PostgresStore/evidence/simulation paths, model-run checks are used by benchmark run validation and promotion planning, benchmark parsing is used by benchmark run validation and promotion planning, benchmark workflow gates are used by schedule-run and benchmark-run recording before compute maps errors, benchmark case readiness normalizes per-case blocking reasons after latest benchmark/model-run lookup, status invariants are used by the catalog status workflow, promotion gate policy is used after benchmark case results are assembled, and production governance gate policy is used after catalog status/hash lookup while snapshot mutation/HTTP mapping remain here.
26. Worker register, claim, and heartbeat domain behavior lives in `apps/api/internal/domain/workers.WorkerLifecycleService`; this package keeps only a `workerStoreAdapter` from existing `WorkerStore` / job records into the domain package. Worker artifact upload and succeed/fail completion remain separate job/artifact lifecycle paths.
27. Result read, evidence package export, production readiness, and evidence-ref resolution live in `EvidenceGovernanceService`; its constructor should stay limited to `EvidenceGovernanceStores` (`JobStore`, `ModelRunStore`, `ProcessGraphStore`), the contract validator, a clock, model catalog resolver callback, artifact listing callback, and artifact metadata callback. Stable evidence package input ref extraction, evidence ref parsing, stored result summary risk projection, result explanation evidence ref extraction, simulation input payload lookup, risk finding summary, and production-readiness policy helpers live in `apps/api/internal/domain/evidence`; the stable model-run production governance allowed predicate delegates to `apps/api/internal/domain/models`. The service must remain read-only and must not mutate jobs, model catalog snapshots, artifacts, or approval state.
28. Job status constants, terminal/worker-result status invariants, failed-worker fallback result construction, worker result completion status/error extraction, and worker claim capability/contract-version matching live in `apps/api/internal/domain/jobs`; this package keeps compatibility aliases and store-level projection calls. Job create/list/read/events, cancel, complete/fail, timeout sweep, and persisted model-run validation/persistence orchestration live in `JobLifecycleService`; its constructor should stay limited to `JobStore`, `ModelRunStore`, the contract validator, a clock, and artifact listing callback. Stable failed-worker fallback result construction and worker-result completion interpretation live in `apps/api/internal/domain/jobs`, the stable compute result model_run extraction/precheck lives in `apps/api/internal/domain/models`, and job lifecycle still owns schema validation, raw persistence adapter, result hash, summary persistence, and store writes. Job lifecycle may persist job events/results/model runs but must not perform artifact object writes, model catalog mutations, or evidence package generation.
29. Metrics snapshot reads live in `apps/api/internal/platform/metrics.MetricsService`; this package keeps only compatibility aliases plus the concrete Memory/Postgres `MetricsStore` implementations. The metrics service constructor should stay limited to a snapshot store and a clock. It must remain read-only and must not trigger retention sweep, timeout sweep, job mutation, artifact mutation, or archive mutation.
30. Selected mutation audit envelopes currently live in `compute_job_events.event_json.audit` for `job.created` / `job.queued` and artifact retention delete/archive events. HTTP-triggered paths capture the static-token principal and route; non-HTTP scheduler/service paths fall back to system/service context. This is not yet full all-mutation audit or OIDC/RBAC. Tenant/project/site read-scope is currently enforced for job list/get and artifact download; full object-level data-scope enforcement remains future work.
31. Internal domain service constructors must not accept aggregate `Store` directly and should expose at most three store-like constructor parameters. `scripts/audit-compute-api-boundary.ps1` records `service_constructor_boundaries` and fails on aggregate `Store` regressions or over-wide internal constructor signatures. Public `NewService` / `NewServiceWithArchive` may keep aggregate `Store` while this package owns compatibility wiring.
32. Agent constraint application advisory plan assembly and Agent draft proposed request extraction live in `apps/api/internal/domain/agent`, artifact retention policy helpers and sweep action planner live in `apps/api/internal/domain/artifacts`, evidence input/ref/risk parsing, stored result summary risk projection, result explanation evidence ref extraction, and readiness policy evaluation live in `apps/api/internal/domain/evidence`, job status, failed-worker fallback result construction, worker result completion, and worker claim matching invariants live in `apps/api/internal/domain/jobs`, built-in model catalog document shape, benchmark case run job document shape, compute result model_run extraction/precheck, model run raw parsing, model-run identity checks, benchmark run evidence-ref parsing, benchmark workflow gates, benchmark case readiness, parameter-set status invariants, promotion gate policy, and production governance gate live in `apps/api/internal/domain/models`, simulation execution profile, simulation check job document assembly, and process graph validation/projection helpers live in `apps/api/internal/domain/simulation`, and worker lifecycle lives in `apps/api/internal/domain/workers`. Platform-level static bearer token parsing lives in `apps/api/internal/platform/auth`, runtime config lives in `apps/api/internal/platform/config`, schema loading / schema_version mapping / JSON Schema validation / base document validation response lives in `apps/api/internal/platform/contracts`, HTTP helpers such as JSON response writing and local loopback CORS live in `apps/api/internal/platform/httpx`, and metrics snapshot / read-only collector / Prometheus rendering live in `apps/api/internal/platform/metrics`. This package may use domain/platform helpers, but domain and platform packages must not import compute compatibility types. Compute still owns artifact object/archive execution and audit envelopes because they depend on current object stores and metadata records, job record/store wiring, job-specific tenant/project/site data-scope checks because those depend on `JobRecord`, model_run schema validation/raw persistence and store writes because they depend on current validators and stores, job result persistence because it depends on current job lifecycle stores and compute_result schema validation, model catalog / benchmark workflow DTOs, material-balance default parameter hash and catalog DTO conversion because they use compute hash/DTO types, benchmark schedule-run catalog lookup/gate/error mapping/execution profile lookup/simulation input resolution/JSON marshaling/createJob because they depend on current validators, services, callbacks, and job lifecycle, compute DTO decode because it returns compute types, draft confirmation response attachment because it depends on `DraftConfirmationRecord`, draft confirmation lookup/schema validation/promotion because those depend on current confirmation records, validator, and simulation-check callback, simulation request schema validation and input_ref resolution because they depend on current validators/stores, simulation input/process graph metadata persistence and schema/store orchestration because they depend on current metadata records and validators, evidence package / production-readiness response assembly because it depends on current compute DTOs and callbacks, and concrete Memory/Postgres metrics count queries because they depend on metadata storage.

## 7. AI 操作提示

API 行为变化需同步 `apps/api/openapi/compute.openapi.json`、generated compute client and `.ai/changes`。
