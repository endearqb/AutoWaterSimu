# 目录说明：apps/api/internal/compute

## 1. 目录职责

本目录实现 Go Compute API Phase 4A compute lifecycle。

本目录负责：

- Job create/get/list/cancel/result/events。
- Worker register/claim/heartbeat/artifact/succeed/fail。
- Model catalog snapshot registration/read/list endpoints with tenant/project/site scoped reads for persisted snapshots, scoped registration/status mutation checks, default parameter set status transitions, read-only default parameter set promotion plans, evidence-backed default parameter set approval promotion, and benchmark case job scheduling。
- Model benchmark case metadata and queueing for governance smoke。
- Benchmark run execution history persistence/list/read endpoints。
- Model run persistence plus read/list lookup。
- Process graph registry and ProcessGraph-to-SimulationInput resolution for simulation checks。
- Simulation input registry used by reference-based simulation checks。
- Evidence package export from completed job metadata。
- Simulation check creation from `simulation_request.v1` into queued `compute_job.v1`。
- Artifact retention metadata recording。
- Risk findings copied into stored result summary for read-only integrations。
- Evidence reference dereference for model run, artifact, job, process graph, and embedded simulation input refs。
- Evidence governance summary generated from model runs and the job-scoped latest persisted model catalog when job tenant/project/site is present, with unscoped latest persisted / built-in fallback。
- Read-only production readiness report generated from evidence governance and stored risk findings。
- Contract validation for existing Agent / simulation / constraint draft / draft confirmation / result explanation schema files。
- Draft confirmation audit record persistence/readback plus tenant/project/site read-scope on confirmation, plan, and promotion paths。
- Read-only advisory constraint application plan generation for approved constraint draft confirmations。
- Result explanation submit/review/publish audit workflow with job-scoped evidence ref checks。
- Explicit approved Agent draft promotion to simulation-check jobs when the embedded proposed request is schema-valid。
- Admin-scoped artifact retention sweep HTTP endpoint with safe dry-run default and tenant/project/site scoped candidate filtering。
- Disabled-by-default artifact retention scheduler helper。
- Opt-in local filesystem or S3-compatible archive backend metadata and download fallback。
- Prometheus metrics snapshot rendering through a read-only metrics service, including archived artifact metadata count。
- Static bearer token scope auth with config-level revocation。
- Token-scoped tenant/project/site read filtering for job list/get, process_graph get, simulation_input get, draft confirmation get / constraint plan / promotion, persisted model catalog root/model/snapshot reads, model_run get / job-filtered list, benchmark_run get / job-filtered list, artifact download, and evidence governance model catalog selection for scoped jobs; plus direct job create, direct job cancel, artifact retention sweep candidate filtering, worker claim candidate filtering, worker heartbeat/artifact/result completion job mutation, confirm-draft record persistence, result explanation submit/review/publish, direct simulation-check create, draft promotion job create, benchmark schedule-run job create, model catalog registration/status, benchmark_run registration, and explicit process_graph/simulation_input registry POST mutation data-scope checks。
- Selected mutation audit event envelopes for job create/queue, job cancel/timeout, worker registration and worker claim/heartbeat/artifact upload/result completion, draft confirmation, draft promotion / benchmark schedule-run job create/queue, artifact retention delete/archive, result explanation submit/review/publish, non-job-scoped model governance mutations, and simulation registry registration mutations。
- Contract validation、canonical payload hash、idempotency/conflict。
- Metadata store abstraction and PostgreSQL implementation。

本目录不负责：

- Python simulation execution。
- Desktop local runtime。
- Frontend UI。

## 3. 维护约定

1. Create job idempotency and payload conflict behavior must stay deterministic.
2. List APIs use stable cursor pagination.
3. Worker state transitions must be validated server-side.
4. Error responses should map to `contract_error.v1`-style structures where applicable.
5. Local development CORS is intentionally limited to loopback browser origins for Web UI smoke tests; checksum visibility is limited to exposed `X-Artifact-Checksum` / `X-Evidence-Checksum` headers; do not broaden origins or exposed headers without an explicit deployment/auth review.
6. Successful compute results may include `runtime_audit.model_runs`; stable extraction and present `job_id` consistency precheck live in `apps/api/internal/domain/models`, while schema validation, raw JSON persistence adapter, and store writes stay in job lifecycle. Persist schema-valid `model_run.v1` records without storing large artifact contents in metadata tables, and keep list filters limited to indexed governance fields such as `job_id`、`model_key` and `model_version`.
7. Evidence package export must reference artifacts/model runs by id and include a checksum header that browser clients can read through the local CORS expose list; do not inline artifact bytes.
8. Contract validation endpoints use existing `job:create` scope; `/contracts/validate` validates only schema files compiled by `ContractValidator` through the platform contracts document validation helper, while `/contracts/confirm-draft` additionally validates the embedded draft, constrains scoped tokens to the draft confirmation payload metadata before persistence, persists a draft confirmation audit record, writes compact `draft_confirmation.recorded` mutation audit on first insert only, and returns a warning that no compute job was created. Stable draft confirmation wrapper / embedded draft cross-field validation and record data projection live in `apps/api/internal/domain/agent`; schema file lookup, JSON Schema validation, compute `DraftConfirmationRecord` mapping, response attachment, and store writes remain here. `/contracts/confirmations/{confirmation_id}` and `/contracts/confirmations/{confirmation_id}/constraint-application-plan` use `job:read`; both read paths constrain scoped tokens to the stored confirmation `tenant_id` / `project_id` / `site_id`. Constraint plans require an approved `constraint_draft.v1` confirmation and return advisory metadata only; they must not create compute jobs, mutate the target, or mark production approval complete. Stable advisory plan shape and warnings live in `apps/api/internal/domain/agent`. `/contracts/confirmations/{confirmation_id}/promote-simulation-check` is the only promotion path: it requires `job:create`, first constrains scoped tokens to the stored confirmation scope, then promotes only approved `agent_scenario_draft.v1` confirmations with a schema-valid embedded `simulation_request.v1`; scoped promotion also constrains the proposed request, input-ref resolution, and final job create to the same principal data scope so a matching confirmation cannot smuggle a cross-scope simulation request. Stable proposed request extraction lives in `apps/api/internal/domain/agent`, while schema validation and job creation stay here. Unknown future contracts must remain invalid until the schema exists.
9. Static token rotation is represented by overlapping token config and setting old token records to `revoked=true`; revoked tokens must fail authentication even if their scopes match. Token config may include `tenant_id`, `project_id`, and `site_id`; when present, job list/get, process_graph get, simulation_input get, draft confirmation get / constraint plan / promotion, persisted model catalog root/model/snapshot reads, model_run get / job-filtered list, benchmark_run get / job-filtered list, and artifact download HTTP reads must be constrained to matching stored object/job context. Scoped direct `POST /api/v1/compute/jobs` must match `compute_job.context` tenant/project/site before any job/event write. Scoped direct `POST /api/v1/compute/jobs/{job_id}/cancel` must match the stored job tenant/project/site before cancel state/event writes. Scoped artifact retention sweep filters candidates by the token tenant/project/site before reporting or deleting/archiving artifact metadata and objects. Scoped worker claim filters candidate queued jobs to the token data scope, and scoped worker heartbeat/artifact upload/result completion must match the stored job tenant/project/site before mutating worker/job/artifact state. Scoped direct `POST /api/v1/simulation-checks` must match request metadata scope before input-ref resolution and job/registry writes; embedded simulation input metadata inherits the authorized request scope only when missing. Scoped draft promotion must match both the stored confirmation scope and the proposed simulation request / input-ref / final job scope before job or registry writes. Scoped benchmark schedule-run must match the referenced simulation input / process graph / model_run source job scope and request metadata-derived job scope before job writes. Scoped model catalog reads only consider matching persisted snapshots and may fall back to the built-in reference catalog when no matching persisted snapshot exists; scoped model catalog registration must match payload tenant/project/site metadata, scoped default-parameter-set status/promote-approved mutations must mutate a matching persisted catalog instead of the built-in/global catalog, scoped benchmark_run registration must match the payload `job_id` associated job scope before any benchmark run or mutation audit write, and scoped explicit process_graph/simulation_input registry POST must match payload tenant/project/site metadata before any registry or mutation audit write. Scoped tokens must include an authorized `job_id` when listing `/api/v1/model-runs`, listing `/api/v1/model-catalog/{model_key}/versions/{model_version}/benchmark-runs`, reading a default-parameter-set promotion plan, or calling promote-approved; unfiltered model_run / benchmark_run lists and unfiltered promotion evidence remain global-token only. Empty tenant/project/site remains global for existing dev/admin tokens. Explanation submit/review/publish mutations require `explanation:write` in addition to the route-level read boundary.
10. Model catalog GET endpoints use `job:read`; `POST /api/v1/model-catalog` uses `model:write` to register schema-valid `model_catalog.v1` snapshots. Scoped registration must match payload tenant/project/site metadata before any store write. Reads prefer the latest persisted `default` catalog and fall back to the built-in catalog when no snapshot exists. The built-in catalog includes material_balance with an approved default parameter set plus ASM1Slim/ASM1/ASM3/UDM worker-smoke-backed model versions and benchmark cases without default parameter sets. Its stable document shape lives in `apps/api/internal/domain/models`; material-balance default parameter hash generation, typed DTO conversion, contract schema validation, persisted snapshot preference, store writes, and HTTP response mapping remain here. `GET /api/v1/model-catalog/snapshots` lists persisted snapshots only and does not emit the built-in fallback as history. `GET /api/v1/model-catalog/{model_key}/versions/{model_version}/default-parameter-set/promotion-plan` is advisory-only: it checks latest benchmark_run/model_run evidence for the current default parameter set and reports whether a `validated` set is ready to be manually promoted to `approved`; it must not execute benchmarks, mutate catalog snapshots, or mark production approval complete. Scoped tokens must provide an authorized `job_id`, and the plan then considers only benchmark/model_run evidence for that job. `POST /api/v1/model-catalog/{model_key}/versions/{model_version}/default-parameter-set/promote-approved` uses `model:write`, reuses the same promotion plan as a gate, and only then stores a new catalog snapshot that changes the current default parameter set to `approved`; scoped tokens must provide an authorized `job_id`, reuse the job-scoped promotion plan gate, and mutate only a matching persisted catalog, while no matching persisted catalog returns 403 instead of falling back to built-in/global catalog. It must not execute benchmarks, record `benchmark_run.v1`, or mark production approval complete. `POST /api/v1/model-catalog/{model_key}/versions/{model_version}/benchmark-cases/{benchmark_case_id}/schedule-run` uses `job:create` and only queues a standard `compute_job.v1` for an active model version's validated benchmark case after resolving the existing simulation input reference and checking the current default parameter set exists and is not retired; scoped tokens constrain the referenced input-ref object and final job context before writes. Its stable job document shape lives in `apps/api/internal/domain/models`; catalog lookup, gate/error mapping, execution profile lookup, simulation input resolution, JSON marshaling, idempotent createJob, store writes, and HTTP response mapping remain here. It does not execute Python, record `benchmark_run.v1`, mutate catalog snapshots, or mark production approval complete. `POST /api/v1/model-catalog/{model_key}/versions/{model_version}/default-parameter-set/status` updates the existing default parameter set status through allowed forward transitions or retirement and stores a new catalog snapshot; scoped tokens mutate only matching persisted catalogs, and no matching persisted catalog returns 403 instead of falling back to built-in/global catalog. This is still not multi-parameter-set management or an automated approval workflow.
11. Benchmark run history endpoints record schema-valid `benchmark_run.v1` only after checking the target benchmark case is present/validated, the parameter set matches the current default parameter set, the referenced model_run exists with matching model/version/parameter hash, and evidence refs resolve inside the model_run job. Scoped registration checks the payload `job_id` associated job tenant/project/site before store/audit writes. They must not create or execute benchmark jobs, mutate parameter set status, or mark production approval complete. List queries may filter by `job_id`, `benchmark_case_id`, and `parameter_set_id`; scoped tokens must provide an authorized `job_id`. Promotion plan and promote-approved use the newest passed run per validated benchmark case for the current default parameter set, and scoped calls add the authorized `job_id` filter before evidence lookup.
12. Artifact upload defaults `retention_policy` to `retain_forever`; when workers provide `ttl` / `archive_candidate` and optional `retain_until`, the API records those fields. `POST /api/v1/admin/artifacts/retention-sweep` requires `artifact:admin`, defaults to `dry_run=true`, filters candidates by scoped token tenant/project/site before reporting or mutating artifacts, can delete expired unreferenced `ttl` artifacts, and writes an audit event envelope; artifacts referenced by model_run evidence refs are protected. When `archiveArtifacts` is configured, expired unreferenced `archive_candidate` artifacts are copied to the configured archive backend (`local_fs_archive` or path-style `s3_archive`), checksum-verified, recorded in durable archive metadata, logged as `artifact.archived`, and then removed from hot storage while normal artifact download falls back to the archive copy. Without an archive store, `archive_candidate` remains skipped with `archive_executor_not_configured`. Archive handling must follow `.ai/decisions/0010-artifact-archive-backend-boundary.md`. The scheduler helper reuses this service method with no token scope and is only started by the command entrypoint when explicitly configured.
13. When a valid `compute_result.v1` includes top-level `risk_findings`, copy those findings into the stored summary through `apps/api/internal/domain/evidence.StoredResultSummary` so result read APIs expose them without storing the full result payload in metadata tables. Job lifecycle still owns schema validation, result hashing, persistence, and failed-worker completion parsing after `apps/api/internal/domain/jobs.FailedWorkerComputeResult` constructs the fallback result document. Evidence-read integrations can call `GET /api/v1/compute/jobs/{job_id}/evidence-ref?ref=...` to resolve supported refs only within that job boundary; do not dereference refs across unrelated jobs. Supported refs are `model_run:<id>`、`artifact:<id>`、`job:<id>`、`simulation_input:<id>`、`process_graph:<id>` and generated `evidence_package:<id>`；stable evidence ref parsing lives in `apps/api/internal/domain/evidence`.
14. Evidence governance uses the latest persisted model catalog, with built-in fallback, to mark model version and parameter set status; `production_allowed=true` currently requires an active model version and matching approved default parameter set. That pure model-run production governance gate lives in `apps/api/internal/domain/models`, while store-backed catalog lookup and evidence package assembly remain here. `GET /api/v1/compute/jobs/{job_id}/production-readiness` uses `evidence:read` and returns schema-valid `production_readiness.v1`: job not succeeded, `governance.production_allowed=false`, or high/critical `risk_findings` block readiness; medium findings only warn. The stable `risk_findings` extraction, severity summary, and production-readiness policy evaluation rules live in `apps/api/internal/domain/evidence`. The report is read-only, keeps `external_approval_required=true` and `auto_publish_allowed=false`, and must not mutate jobs/catalogs or mark production approval complete.
15. Process graph registration stores only schema-valid `process_graph.v1` payload metadata and hash in the metadata DB, including optional `tenant_id` / `project_id` / `site_id` copied from document metadata for GET read-scope checks. Scoped explicit `POST /api/v1/process-graphs` registration must match payload tenant/project/site metadata before any store or mutation audit write. First writes also persist compact `process_graph.registered` audit events in `mutation_audit_events` without embedding the full process graph payload; duplicate same-hash upserts do not duplicate audit. Stable material-balance process graph structure validation, ProcessGraph-to-SimulationInput projection, and neutral process graph record data projection live in `apps/api/internal/domain/simulation`; this package keeps schema validation, compute `ProcessGraphRecord` mapping, idempotency, store access, HTTP mapping, and evidence-ref lookup. The API currently resolves `simulation_request.v1.input_ref.process_graph_id` by loading a registered process graph and generating a `simulation_input.v1` payload for material-balance jobs; it does not execute simulation directly and must not infer ASM/UDM process graph semantics.
16. Simulation check creation is a thin adapter from external `simulation_request.v1` to internal `compute_job.v1`; direct HTTP simulation-check create validates request metadata tenant/project/site scope before input-ref resolution, then validates embedded `input_ref.simulation_input`, resolves a previously registered `input_ref.simulation_input_id`, or replays a persisted `input_ref.model_run_id` by reusing the source job's original `simulation_input.v1` payload before queueing for material_balance/ASM1Slim/ASM1/ASM3/UDM job types. Embedded `simulation_input` payloads inherit authorized request tenant/project/site metadata when those fields are missing so auto-created registry records are scoped; explicit embedded metadata mismatches are rejected before registry/job writes. The stable job type to execution profile / worker capability mapping and pure simulation check job document assembly live in `apps/api/internal/domain/simulation`. Registered `input_ref.process_graph_id` resolution remains material-balance-only.
17. Simulation input registration stores only `simulation_input.v1` payload metadata and hash in the metadata DB, including optional `tenant_id` / `project_id` / `site_id` copied from document metadata for GET read-scope checks. Scoped explicit `POST /api/v1/simulation-inputs` registration must match payload tenant/project/site metadata before any store or mutation audit write. First writes also persist compact `simulation_input.registered` audit events in `mutation_audit_events` without embedding the full simulation input payload, including simulation-check auto-created registry records. Stable neutral simulation input record data projection lives in `apps/api/internal/domain/simulation`, while this package keeps schema validation, compute `SimulationInputRecord` mapping, idempotency, store access, HTTP mapping, and evidence-ref lookup. It must not store simulation results, time-series artifacts, or approval state.
18. Result explanation workflow stores externally generated `result_explanation.v1` payloads only after schema validation and job-scoped evidence ref resolution. Stable top-level and statement-level result explanation evidence ref extraction plus neutral record data projection live in `apps/api/internal/domain/evidence`. Submit/review/publish mutations write compact `compute_job_events.event_json.audit` envelopes without embedding the full explanation payload. Review/publish changes audit status only; it must not generate explanation text, execute Agent code, mark production approval complete, or mutate jobs/results.
19. `/metrics` renders a read-only snapshot from the metadata store: API up, jobs by status, registered workers, artifact metadata count, archived artifact metadata count, and retention candidates. Metrics rendering must not trigger retention sweep, timeout sweep, or any lifecycle mutation.
20. `Store` is the aggregate metadata store. Domain metadata interfaces live in `store_interfaces.go`; the in-memory implementation remains one `MemoryStore` type but its methods are split across `memory_*.go` domain files. Artifact metadata uses `ArtifactMetadataStore` because `artifacts.go` already owns the byte/object `ArtifactStore` abstraction.
21. Artifact upload, job artifact listing, artifact metadata lookup, download, retention sweep, and archive copy/checksum/delete logic live in `ArtifactLifecycleService`; same-package workflow methods are grouped across `artifact_lifecycle_upload.go`, `artifact_lifecycle_read.go`, `artifact_lifecycle_retention.go`, and `artifact_lifecycle_archive.go`, while `artifact_lifecycle.go` keeps struct/constructor/store/object-store wiring. Its constructor should stay limited to `ArtifactLifecycleStores` (`JobStore`, `ArtifactMetadataStore`, `ArchiveMetadataStore`), `ArtifactObjectStores` (hot and archive object stores), the contract validator, and a clock. Stable artifact retention policy parsing, candidate checks, and retention sweep action planning live in `apps/api/internal/domain/artifacts`.
22. Simulation input registration, process graph registration, `simulation_request.input_ref` resolution, material-balance ProcessGraph-to-SimulationInput schema/store orchestration, model-run replay input lookup, and compact registry audit construction live in `SimulationInputService`; same-package workflow methods are grouped across `simulation_inputs_registry.go`, `simulation_inputs_process_graphs.go`, `simulation_inputs_resolution.go`, and `simulation_inputs_audit.go`, while `simulation_inputs.go` keeps struct/constructor/store wiring. Its constructor should stay limited to `SimulationInputStore`, `ProcessGraphStore`, `ModelRunReplayStore` (`ModelRunStore` + `JobStore`), the contract validator, and a clock.
