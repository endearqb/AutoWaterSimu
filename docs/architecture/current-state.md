# AutoWaterSimu Next Current State

> Snapshot date: 2026-06-04.

This document summarizes long-lived facts from README files, `.ai/decisions/`, release gate scripts, and the Certainty/Elegance quality plan. It does not replace source code, tests, OpenAPI, contracts, or `.ai/changes/`.

## Landed

- README First protocol is active through `AGENTS.md`, `README_First.md`, directory README files, `.ai/changes/`, and `.ai/decisions/`.
- Next monorepo surfaces exist beside legacy `frontend/` and `backend/`: `contracts/`, `apps/api/`, `services/simulation-worker/`, `apps/desktop/`, and `simulation_core/`.
- `contracts/` contains versioned JSON Schemas, a registry, a codegen/validation policy manifest, valid/invalid examples, and contract tests.
- `contracts/desktop_project_package.v1.json` and `contracts/desktop_support_bundle.v1.json` define the Desktop project package and support bundle wire shapes with valid/invalid fixtures.
- `ontology/` contains the first Water Ontology registries for objects, actions, links, and policies; `docs/architecture/ontology-model.md` records their purpose and runtime enforcement boundary.
- `scripts/check-ontology.ps1` validates Water Ontology schema versions, unique keys, object/action/link/policy references, and required descriptive fields.
- `apps/api/` exposes the Go Compute API with job lifecycle, worker lifecycle, artifacts, model governance, evidence, simulation checks, result explanation workflow, production readiness, metrics, retention, and archive boundaries.
- `apps/api/internal/compute/http.go` keeps the HTTP server entrypoint and unchanged route registration block, while route handlers are split by group across `http_jobs.go`, `http_artifacts.go`, model governance `http_model_*.go` / `http_benchmark_runs.go`, `http_contracts.go`, `http_simulation.go`, `http_workers.go`, and `http_metrics.go`.
- `apps/api/internal/compute/store_interfaces.go` expresses the aggregate metadata `Store` as 12 embedded domain store interfaces, while `memory_*.go` files keep the in-memory `MemoryStore` implementation split by domain in the same package.
- `apps/api/internal/compute/postgres.go` keeps the PostgreSQL store entrypoint and migration apply/check helpers, while `postgres_*.go` files keep PostgreSQL metadata persistence split by domain in the same package; model governance persistence is further split across model run, benchmark run, and model catalog files.
- `apps/api/internal/compute/artifact_lifecycle.go` keeps `ArtifactLifecycleService` struct/constructor/store/object-store wiring, while same-package `artifact_lifecycle_*.go` files group artifact upload, listing/metadata lookup/download fallback, retention sweep, and archive copy/checksum/delete workflows.
- `apps/api/internal/domain/agent` owns stable draft confirmation envelope validation, draft confirmation record data projection, constraint application advisory plan assembly, and Agent draft proposed request extraction; `compute` keeps schema file lookup, JSON Schema validation, compute record mapping, approval/schema gating, promotion job creation, persistence, and HTTP mapping.
- `apps/api/internal/domain/artifacts` owns stable artifact retention policy parsing, candidate checks, and sweep action planning; `compute` keeps object storage, archive execution, metadata persistence, audit envelopes, and HTTP mapping.
- `apps/api/internal/domain/evidence` owns stable evidence package input reference extraction, evidence ref parsing, stored result summary risk projection, result explanation evidence ref extraction, result explanation record data projection, embedded simulation input payload lookup, `risk_findings` extraction/summary rules, and production-readiness policy evaluation; `compute` keeps job completion persistence, result explanation schema validation/job availability/evidence resolution/record mapping/persistence/review-publish mutations, store-backed evidence governance, response DTOs, model catalog/artifact/process graph callbacks, and HTTP mapping.
- `apps/api/internal/compute/simulation_inputs.go` now keeps `SimulationInputService` struct/constructor/store wiring, while same-package `simulation_inputs_*.go` files group simulation input registry/read, process graph registry/projection, `simulation_request.input_ref` resolution, and model-run replay workflows.
- `apps/api/internal/compute/draft_workflows.go` now keeps `DraftWorkflowService` struct/constructor/callback wiring, while same-package `draft_workflows_*.go` files group draft confirmation validation/persistence/read, constraint application planning, and explicit simulation-check promotion workflows; draft confirmation envelope validation and record data projection use `apps/api/internal/domain/agent`.
- `apps/api/internal/compute/result_explanations.go` keeps `ResultExplanationService` constructor/callback wiring while `result_explanations_*.go` groups submit/read/review-publish workflows behind domain store interfaces; result explanation evidence ref extraction plus record data projection now use `apps/api/internal/domain/evidence`.
- `apps/api/internal/compute/model_governance.go` now keeps `ModelGovernanceService` struct/constructor/store wiring, while same-package `model_governance_*.go` files group model catalog, default parameter set promotion planning, benchmark case queueing, benchmark run history, and model run lookup workflows behind domain store interfaces.
- `apps/api/internal/domain/jobs` owns stable compute job status constants, terminal/worker-result status invariants, failed-worker fallback result construction, worker result completion status/error extraction, and worker claim capability/contract-version matching; `compute` keeps compatibility aliases plus MemoryStore/PostgresStore projection calls and persistence/HTTP wiring.
- `apps/api/internal/domain/models` owns stable built-in `model_catalog.v1` document shape, benchmark case schedule-run `compute_job.v1` document shape, `compute_result.v1.runtime_audit.model_runs` extraction/precheck, `model_run.v1` raw identity/evidence refs/warnings/parameter_hash extraction, model-run identity/hash checking, `benchmark_run.v1` evidence refs extraction, benchmark case scheduling / benchmark run admission gates, single benchmark case promotion readiness, default parameter set status transition invariants, promotion gate policy, and model_run production governance gate; `compute` keeps material-balance default parameter hash generation, typed catalog DTO conversion, model_run schema validation/persistence, model catalog governance, catalog snapshot mutation, benchmark workflow orchestration, benchmark schedule-run catalog lookup/gate/error mapping/execution profile lookup/simulation input resolution/createJob, persistence implementation, evidence/simulation wiring, DTOs, and HTTP mapping.
- `apps/api/internal/domain/simulation` owns stable simulation job type execution profile / worker capability mapping, pure simulation check `compute_job.v1` document assembly, material-balance process graph validation/projection rules, and simulation input/process graph record data projection used by simulation-check creation, benchmark case queueing, process graph registration validation, ProcessGraph-to-SimulationInput resolution, and simulation registry record assembly; `compute` keeps simulation request schema validation, input_ref resolution, simulation input/process graph metadata persistence, compute record mapping, schema/store orchestration, HTTP, and model governance wiring.

## Accepted Current Gaps

- `apps/api/internal/compute` is still a large compatibility wiring package. The aggregate `Store` resolves to 41 methods across 12 embedded domain metadata interfaces, the in-memory `MemoryStore` implementation is split across same-package `memory_*.go` domain files, HTTP handlers are split across same-package route-group files while preserving `Routes`, and model governance HTTP mapping is further split across catalog, parameter set, benchmark case, benchmark run, and model run files. PostgreSQL persistence is split across same-package `postgres_*.go` domain files, with model governance persistence further split across `postgres_model_runs.go`, `postgres_benchmark_runs.go`, and `postgres_model_catalog.go`, and the public `Service` compatibility delegates are split across same-package `service_*.go` domain files while `service.go` keeps only struct and constructor wiring. Job lifecycle workflow methods are split across same-package `job_lifecycle_*.go` files while `job_lifecycle.go` keeps constructor/callback wiring; artifact lifecycle workflow methods are split across same-package `artifact_lifecycle_*.go` files while `artifact_lifecycle.go` keeps constructor/store/object-store wiring; model governance workflow methods are split across same-package `model_governance_*.go` files while `model_governance.go` keeps constructor/store/callback wiring; evidence governance workflow methods are split across same-package `evidence_governance_*.go` files while `evidence_governance.go` keeps constructor/callback wiring; simulation input/process graph workflow methods are split across same-package `simulation_inputs_*.go` files while `simulation_inputs.go` keeps constructor/store wiring; draft workflow methods are split across same-package `draft_workflows_*.go` files while `draft_workflows.go` keeps constructor/callback wiring; result explanation workflow methods are split across same-package `result_explanations_*.go` files while `result_explanations.go` keeps constructor/callback wiring. Artifact lifecycle including upload/listing, simulation input/process graph, draft workflow, result explanation, model governance, evidence governance, job lifecycle, and metrics paths now have narrowed constructors. Draft confirmation envelope validation, draft confirmation record data projection, constraint application advisory plan assembly, and Agent draft proposed request extraction have moved to `apps/api/internal/domain/agent`; artifact retention policy helpers and sweep action planner have moved to `apps/api/internal/domain/artifacts`; evidence input/ref/risk parsing, stored result summary risk projection, result explanation evidence ref extraction, result explanation record data projection, and readiness policy helpers have moved to `apps/api/internal/domain/evidence`; job status, failed-worker fallback result construction, worker result completion, and worker claim matching invariants have moved to `apps/api/internal/domain/jobs`; stable built-in `model_catalog.v1` document shape, benchmark case schedule-run `compute_job.v1` document shape, `compute_result.v1.runtime_audit.model_runs` extraction/precheck, `model_run.v1` raw parsing, model-run identity/hash checking, `benchmark_run.v1` evidence ref parsing, benchmark workflow gates, benchmark case readiness, default parameter set status transition invariants, promotion gate policy, and model_run production governance gate have moved to `apps/api/internal/domain/models`; simulation execution profile, simulation check job document assembly, material-balance process graph validation/projection helpers, and simulation input/process graph record data projection have moved to `apps/api/internal/domain/simulation`; and worker register/claim/heartbeat has moved to `apps/api/internal/domain/workers` behind a compute adapter. The architecture audit fails if internal domain/platform service constructors accept aggregate `Store` or expose more than three store-like parameters. Platform audit/auth/config/contracts/HTTP/metrics helpers, the base contract document validation response, and the read-only metrics collector moved to `apps/api/internal/platform/audit`, `apps/api/internal/platform/auth`, `apps/api/internal/platform/config`, `apps/api/internal/platform/contracts`, `apps/api/internal/platform/httpx`, and `apps/api/internal/platform/metrics`, but full domain workflows such as full artifact lifecycle, full models governance, full evidence governance, full simulation input/process graph metadata service handling, full agent draft workflow, full result explanation workflow, and full jobs lifecycle have not moved yet. Package-level wiring, public `NewService` / `NewServiceWithArchive` signatures, and some handler-facing behavior still remain in the compatibility package.
- Multi-language generated contract type output for Go, Python, and Rust is not yet implemented; `contracts/codegen/manifest.json` records the current decision to use runtime schema validation or hand-written boundary DTOs for those targets. Desktop package/support-bundle contracts now exist, but Rust generated DTO adoption is still deferred.
- The Next dev compose stack now has initial API runtime smoke evidence for PostgreSQL + MinIO + Compute API + host Python worker. A hosted/manual integration workflow file exists, and nightly now calls it through `workflow_call`, but a real GitHub Actions green run is still pending. Frontend/browser reads, packaged worker first-start timing, and full compose `simulation-worker` container behavior still need dedicated evidence.
- Local `pr-fast` evidence records dirty worktree state; a clean HEAD proof requires running the same lane after the current changes are committed.
- Full production OIDC/RBAC/data-scope policy is not implemented. P0 static tokens remain the current auth model, but production startup now blocks empty token config and default development token values, and security smoke covers token revocation, scope denial, admin-only artifact retention, selected mutation audit envelopes for job create plus artifact retention delete/archive events, and tenant/project/site read-scope on job list/get plus artifact download. Full object-level data scope and all-mutation audit remain incomplete. A hosted/manual security workflow exists, but a real GitHub Actions green run is still pending.
- Browser smoke is mock-backed and route-focused. A hosted/manual workflow file exists, but a real GitHub Actions green run is still pending. It does not prove live backend reads through PostgreSQL/MinIO/worker or a legacy authenticated backend session.
- Desktop package smoke is source-mode runtime focused. A hosted/manual workflow file exists, but a real GitHub Actions green run is still pending. The release artifact download verifier now has fixture-backed smoke coverage and is wired into `next-release-gates.yml`, but a real hosted unsigned artifact upload/download round trip is still pending. This does not prove packaged-worker exe startup, NSIS installer behavior, signing, or auto update.
- Water Ontology has a first registry-backed semantic layer, but it is not yet a runtime policy enforcement layer. Full OIDC/RBAC/ABAC/data-scope and all-mutation audit enforcement remain future work.
- The 8 golden scenarios are not all automated. Existing release gate, worker, contract, Go, frontend, and desktop checks cover many single-lane validations but not every scenario end to end.

## Immediate Quality Direction

The next low-risk increments are:

1. Expand `check-deps` only after existing code is brought into compliance with each new rule.
2. Trigger or wire the hosted integration and browser smoke workflows, then add live backend browser reads on top of the current mock-backed browser lane.
3. Continue Go package movement from `domain/agent` / `domain/artifacts` / `domain/jobs` / `domain/models` / `domain/simulation` / `domain/workers` and the first platform auth/config/contracts/HTTP/metrics packages toward additional domain packages, handler/package surface reduction, and later public constructor signature narrowing while preserving MemoryStore/PostgresStore coverage.
4. Expand scenario-level smoke evidence beyond the current material-balance job path to browser, packaged Desktop worker/installer, security, release, and golden scenario lanes.
5. Promote Desktop package evidence to hosted CI or release-evidence lane before treating the Desktop offline golden scenario as complete.
6. Connect Water Ontology policies to real authorization/data-scope/audit implementation only after the runtime security model is explicit and test-backed.
7. Revisit Go/Python/Rust generated contract and ontology types only after package boundaries and Desktop package runtime validation are stable.
8. Continue production security with real issuer/JWKS or service-token secret integration, data-scope filtering, all-mutation audit coverage, and a security smoke lane.
